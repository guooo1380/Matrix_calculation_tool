# 开发过程

这份文档记录项目从零到现在的真实时间线：每一步解决了什么问题、为什么那样选、踩了哪些坑。
原始素材是一次会话的完整导出（8903 行），体积大且噪音多，没有进版本库，只保留了这份提炼后的记录。

## 阶段一：命令行版（2026-09-21 晚）

起点是一个「计算方阵转置」的单文件脚本 `matrix_transpose.py`，之后按需求一个个往上加功能：

| 顺序 | 加入的功能 | 实现方式 |
|---|---|---|
| 1 | 转置 | 列表推导换下标 |
| 2 | 逆矩阵 | Gauss-Jordan 消元 + 列主元选取（避免小主元放大误差） |
| 3 | 行列式 | 余子式展开递归 |
| 4 | 矩阵乘法 | 三重求和的列表推导，支持任意可乘维度 |
| 5 | 等价标准形 + 秩 | 行列同时消元，返回 `[I_r 0; 0 0]` 与秩 r |

**全程不用 numpy。** 这些是课程练习性质的题目，引第三方库会让练习失去意义，所以算法全部手写，只用标准库——这也成了项目后续的固定约定，写进了 `pyproject.toml` 的零依赖声明里。

随着菜单从 1 项长到 5 项，把重复的输入校验抽成了两个共用函数：`read_matrix(rows, cols, label)` 负责按行读入并校验元素个数和字符合法性，`read_int(prompt, valid=None)` 负责读正整数并可选限定取值集合。矩阵乘法需要一次读两个不同维度的矩阵，正是这次抽取的直接动因。

「把逆矩阵扩展到 n 阶」这个需求实际上不用改算法——Gauss-Jordan 本来就是通用的，只有那一个分支上的 `{2,3,4,5}` 取值校验把阶数卡住了，放开校验即可。转置和行列式仍然保留 2–5 阶的限制，因为行列式是 O(n!) 的递归展开，阶数高了会卡死。

## 阶段二：Tkinter 桌面版与 PyInstaller 打包（2026-09-21 22:45 起）

需求是「做成一个适配 Windows 系统的桌面软件」。此时已经有基于 Tkinter 的 `matrix_gui.py`（下拉选运算 → 填维度 → 生成输入框 → 计算 → 结果区显示），于是用 PyInstaller 打成单文件 exe。

打包本身很顺利，但**双击 exe 闪退**，排查过程比打包本身耗时得多：

- `--windowed` 会吞掉所有异常，看不到任何报错。定位手段是先临时改回 `console=True` 打包，让 traceback 打到控制台。
- 真正的 bug 在 `matrix_gui.py`：`_on_op_change()` 在 `__init__` 里被调用的位置早于 `self.dim_entries = {}` 的初始化，属性还不存在就访问，直接抛异常。开发时从 IDE 里跑不会触发，是因为那条路径的调用顺序不同。
- 想确认进程是否还活着时又踩了两个坑：exe 是中文名，`tasklist | grep` 因为编码问题匹配不上；Git Bash 会把 `tasklist /FI ...` 里的 `/FI` 当成路径去转换，必须写成 `//FI` 或者改用 cmd。

修完重新打包，得到可用的 `dist/矩阵计算工具.exe`。详细步骤和命令见 [打包-Windows.md](打包-Windows.md)。

## 阶段三：安卓版尝试（2026-09-21 23:00 前后，未成功）

需求是「做成适配安卓手机的应用」。当时给了两个方案：Kivy + Buildozer 打原生 APK，或者做网页/PWA。选了 Kivy 方案，于是：

- 把矩阵运算从各版本里抽出来，新建共用模块 `matrix_math.py`（现在的 `src/mathtools/core.py`）。这是项目第一次出现「一份算法、多端复用」的结构，Tkinter 版和 Kivy 版都从它 import。
- 新写 `matrix_kivy.py`（现 `src/mathtools/ui/kivy_app.py`）：Spinner 选运算、TextInput 填维度、GridLayout 铺矩阵单元格，整页放进 ScrollView 以适配小屏。
- 配套 `main.py`（Buildozer 入口）、`buildozer.spec`、`build_apk.sh`（在 WSL Ubuntu 里构建）。

Kivy 这边的坑：

- `TextInput` 不支持 `valign` 参数，传了会在启动时崩溃。结果区的矩阵因此改用「网格 + 只读 Label」渲染，而不是塞进 TextInput，顺带也不再依赖等宽字体对齐。
- 单元格宽度按屏宽动态算：`(可用宽度 - 间距) / 列数`，再夹在 34dp–72dp 之间。34dp 是可点击下限，72dp 是避免 2 列时格子被拉得过宽。
- `buildozer.spec` 必须是 UTF-8 + LF，Windows 上编辑器存成 CRLF 会导致解析异常。这一条现在固化在 `.gitattributes` 里。
- Kivy 2.3.1 必须配 `cython==0.29.36`，cython 3 会破坏 python-for-android 的构建。

**APK 至今没有构建成功。** 环境准备阶段就一路受阻：`wsl --install` 超时，改用 DISM 启用功能 + 重启；Ubuntu 从 GitHub 下载超时（`WININET_E_TIMEOUT`），改从 cloud-images.ubuntu.com 取 24.04 rootfs 再 `wsl --import`；进了 Ubuntu 之后 `dl.google.com`、Gradle 分发、PyPI 全部不可达，会话就在网络错误里终止了。完整的环境准备清单和失败原因见 [打包-Android.md](打包-Android.md)。

为了不改动界面代码就能确认安卓上不出问题，写了两个自检脚本（现 `tests/kivy/`）：`selftest.py` 在 400×780 的窗口里把五种运算和三个异常分支（不可逆、空单元格、维度不匹配）全跑一遍并断言结果；`layoutcheck.py` 检查 2–8 列时网格是否横向溢出、单元格是否还够大、整页能否纵向滚动。

## 阶段四：转向网页 / PWA（2026-09-22 白天）

安卓原生路线被网络卡死后，改走 Web/PWA：一套 HTML/CSS/JS，浏览器能用，也能「添加到主屏幕」当 App 用，完全绕开 SDK/NDK 那套下载链。站点部署在 Netlify，并接了 Netlify Forms 收集用户建议（表单名 `suggestions`）。

这一版的代码和部署配置不在本仓库里，是在另一个工作目录里做的。仓库内的 `webapp/` 是它的界面副本，供阶段五的桌面版复用。

两个值得记下的坑：

- **Netlify 的表单识别默认是关的。** HTML 里 `data-netlify="true"`、`name`、隐藏的 `form-name` 字段全写对了也没用，必须先在后台点 Enable form detection，而且**这个开关只对之后的部署生效**，得重新部署一次。没开的时候 POST 直接返回 404。
- **改 Service Worker 缓存策略时必须同时升 `CACHE` 常量名。** 新旧版本共用一个缓存名时，装过旧版的浏览器会继续拿到缓存里的旧 `index.html`，新功能对用户完全不可见；只有 activate 阶段 `keys.filter(k => k !== CACHE)` 才会清掉旧缓存。

## 阶段五：网页版回灌成 Windows 桌面版（2026-09-22 22:33–22:41）

需求是「把网页版同步到软件版」。做法不是重写界面，而是把网页版原样拷进 `webapp/`，用 pywebview 的 WebView2 窗口渲染 `webapp/index.html`——外观和线上站点完全一致，计算全部在 `app.js` 里完成，Python 侧只负责开窗。

用户建议的提交也搬到 Python 侧：页面跑在 pywebview 的本地静态服务上，直接 `fetch` Netlify 会被跨域拦掉，所以改成 Python 用 `urllib` POST 到线上站点同一个 `suggestions` 收件列表。

- pywebview 默认的 `private_mode` 会在 `%TEMP%` 建随机目录且退出时删不掉，改成固定的 `%APPDATA%/MatrixCalculator`。
- `console=False` 的 exe 报错时什么都不显示，所以专门写了 `_missing_webview2()`，在缺少 WebView2 运行时的情况下用 MessageBox 给出能看懂的提示。
- 打包配置 `矩阵计算工具.spec` 随之改成打 `matrix_desktop.py`，用 `datas=[('webapp', 'webapp')]` 把网页资源带进去，`excludes=['tkinter', '_tkinter']` 去掉用不到的 Tkinter，并指定 `webapp/app.ico` 作为 exe 图标。资源路径通过 `resource_path()` 兼容开发态（脚本同级目录）和 onefile 运行态（`sys._MEIPASS` 解包目录）。

**注意**：这次替换之后，Tkinter 版就没有自己的打包配置了。它仍然可以从源码正常运行（`python -m mathtools.ui.tkinter_app`），只是不再被打包成 exe；Windows exe 现在是 pywebview 桌面版。

## 阶段六：纳入 Git 并按 GitHub 规范整理（2026-09-22 22:29 起）

到这一步项目已经有四种界面，但所有文件都平铺在根目录，构建产物、IDE 配置和一份 396KB 的会话导出混在一起，也没有版本控制。本次整理做了这些事：

- `git init`，补 `.gitignore`（构建产物、缓存、IDE、会话导出原文）、`.gitattributes`（统一 LF，固化 Buildozer 对 spec 文件换行符的要求）、MIT `LICENSE`、`pyproject.toml`（src 布局 + 零运行时依赖 + 按需 extras）、GitHub Actions 工作流跑单元测试。
- 重排成标准 src 布局：`matrix_math.py` → `src/mathtools/core.py`，`matrix_transpose.py` → `src/mathtools/cli.py`，`matrix_gui.py` → `src/mathtools/ui/tkinter_app.py`，`matrix_kivy.py` → `src/mathtools/ui/kivy_app.py`，两个 Kivy 自检脚本 → `tests/kivy/`。
- 消除重复实现：命令行版原本自带一份与 core 完全相同的数学代码，改成 import `mathtools.core`。
- 顺手修掉 `core.transpose` 的潜在坑：它原来用 `len(matrix)` 同时当行数和列数，只能处理方阵，现在对任意 m×n 都正确。
- 测试脚本里硬编码的 `sys.path.insert(0, r"D:\pythonProject\mathTools")` 改成由 `__file__` 推导，换机器也能跑。
- 新增 `tests/test_core.py`，24 个用例覆盖五种运算、奇异矩阵、非方阵转置、格式化输出。
- 提交历史按开发层次拆成若干 Conventional Commits，并用各文件的真实修改时间回填提交日期。
- pywebview 桌面版（`matrix_desktop.py`、`webapp/`）保持原样入库、不挪位置，因为它是并行进行的另一条工作线，且 `resource_path()` 依赖 `webapp/` 与脚本同级的相对关系。它配套的自检脚本随后移到了 `tests/desktop/selftest.py`，与 `tests/kivy/` 的组织方式对齐，`sys.path` 也改成由 `__file__` 推导仓库根。

整理后的验证结果：单元测试 24/24 通过；命令行版五个分支加异常输入全部实跑正确；Tkinter 版脚本化驱动 16/16 通过；Kivy 自测 9/9 通过、布局检查 7/8（唯一一条 WARN 是「整页高 540px 未超过滚动阈值」，属检查脚本自身的启发式判定，非缺陷）；PyInstaller 打包成功产出 exe；`pyproject.toml` 能正确构建出含全部模块的 wheel。

## 阶段七：安卓 APK，绕开 Buildozer（2026-10-26）

需求是「把这个程序打包成一个手机应用」。仓库里早就有一条安卓路线——`src/main.py` + `kivy_app.py` + `buildozer.spec` + `build_apk.sh`，但它从来没成功过，`docs/打包-Android.md` 开头就写着这条结论。

先重新确认环境，发现旧结论已经过期：`dl.google.com`、`services.gradle.org`、`pypi.org`、`registry.npmjs.org` 这次都通。不过本机仍然没有 Java、没有 Android SDK，`JAVA_HOME`/`ANDROID_HOME` 都是空的。

真正改变决策的是另一件事：**`webapp/` 本来就是一套手机界面**。`viewport` 锁缩放、`100dvh`、五个运算 pill、62px 触控格，计算全在 `app.js` 里。手机上并不需要 Python 运行时，一个 WebView 加载本地静态页就够了。于是放弃「编译 CPython + Kivy」，改做 WebView 壳：

| | 要编译 | 下载量 | 结果 |
|---|---|---|---|
| Buildozer | CPython + Kivy + NDK | 10–15 GB | 本机从未成功 |
| WebView 壳 | 一个 Activity | 约 300 MB | 出包 |

因为只有一个 Activity、没有第三方依赖，连 Gradle 也不要，直接手工调 `aapt2` / `javac` / `d8` / `zipalign` / `apksigner`——链路短，每一步失败都能单独定位。

### 环境上的三个坑

1. **本机没有 PowerShell 7**，harness 的 `pwsh` 工具任何命令都返回 `0xC0000142`（DLL 初始化失败，因为 `pwsh` 根本不存在）。绕开的办法是用 Python 直接写文件执行，命令结果落盘再读。
2. **Adoptium 的 JDK 直链不能用**：`api.adoptium.net` 会 302 到 GitHub release 资源，下到 3 MB 就挂住，连读超时都等不到。换微软 OpenJDK（`aka.ms/download-jdk/...`）后稳定在 3–4 MB/s。
3. **`dl.google.com` 极慢且 TLS 不稳**：本机所有流量走 `127.0.0.1:7993` 的本地代理，Python 的 OpenSSL 栈在拉 `cmdline-tools` 时直接报 `SSL: UNEXPECTED_EOF_WHILE_READING`，改用 `curl.exe`（走 Windows Schannel）能下但只有约 200 KB/s。
4. **不要猜 SDK 归档的文件名**。`platform-34_r03.zip`、`platform-34_r02.zip`、`platform-34_r01.zip` 全是 404——真实名字是 `platform-34-ext7_r03.zip`（带扩展级别）。权威来源是 Google 的 [`repository2-3.xml`](https://dl.google.com/android/repository/repository2-3.xml) 索引（413 KB），用 `path="platforms;android-34"` 定位后再从它下面的 `<url>` 取归档名。`build-tools;34.0.0` 则同时挂了 `linux`/`macosx`/`windows` 三个包，必须按 `windows` 挑。
5. **换个镜像，速度差 20 倍**。同样两个包，`dl.google.com` 经代理只有约 200 KB/s（60 MB 的平台包下了 90 秒才 7.5 MB 就明显掉速）；腾讯的 `mirrors.cloud.tencent.com/AndroidSDK/` 直连 4.0–4.3 MB/s，60.3 MB / 15 秒、55.6 MB / 13 秒就完了。脚本因此先试镜像、失败再回落到官方源。

### 手工打包的四个细节

1. **assets 不用 `aapt2 link -A`**，而是在合包阶段用 Python `zipfile` 把 `assets/www/*` 和 `classes.dex` 一起塞进去。dex 与资源编译彻底解耦。
2. **`resources.arsc` 必须 STORED**。targetSdk ≥ 30 时它一旦被 deflate 压缩，Android 11+ 会拒绝安装，报错还很含糊。合包时单独把这一个 entry 设成 `ZIP_STORED`。
3. **先 `zipalign` 后 `apksigner`**。v2 签名是对整个 zip 结构做的摘要，签完再对齐会把签名弄坏。
4. **`javac` 必须 `-bootclasspath android.jar`**。否则 JDK 17 拿自己的 `java.base` 当引导类库，`android.*` 全都找不到。

### 壳层要处理的事

- **离线**：`file://` 下 `fetch('/')` 必然失败，而页面头部的「建议」按钮会 POST 到 Netlify 表单。打包时在 `index.html` 的 `</body>` 前注入一小段脚本，`location.protocol === 'file:'` 时隐藏该按钮。`webapp/` 源文件不动，线上站点行为不变。
- **跳转**：`shouldOverrideUrlLoading` 只放行 `file://`；不申请 `INTERNET` 权限，离线是硬保证而不是自觉。
- **返回键**：不能后退就直接退出（单页应用没有历史栈）。

产物 `dist/矩阵计算工具.apk`，`applicationId` 为 `com.mathtools.matrix`，minSdk 21 / targetSdk 34，竖屏锁定，图标由 `webapp/icon-512.png` 生成五档 mipmap。重建只要一条命令：`python android-build/scripts/build_apk.py`。

### 产物的实测数据

- 447,538 B（0.43 MB），SHA-256 `30b7f1dd…516a5`。
- `aapt2 dump badging`：包名、版本、应用名（中文正常）、五档图标、`sdkVersion:'21'`、`targetSdkVersion:'34'`、竖屏 feature 都在。
- `aapt2 dump permissions` 只输出包名 —— **零权限**。
- `apksigner verify --verbose`：v1(JAR) / v2 / v3 三种签名方案全部 `true`，证书 `CN=MathTools`、RSA 2048。
- `resources.arsc` 在 zip 里是 STORED，`classes.dex` 3.3 KB，`assets/www/` 三个文件与 `webapp/` 逐字节相同，`index.html` 仅多注入的 180 B 脚本。
- **没有真机/模拟器验证**：本机既无 `adb` 也无 `emulator`，所以只证明了包结构与签名合法，运行期行为未实测。这条限制也写进了打包文档。

打包过程中还发现 `build_apk.py` 自身三个会让首次构建失败的问题，都已修掉：`stage()` 没有把 `java/` 拷进暂存目录（`javac` 会拿到空文件列表）、`install_sdk()` 在「组件已存在」的早退分支之前就要求 `sdkmanager` 存在、以及 `apksigner.bat` 没有经过 `cmd /c` 调用。另外 `print()` 在 `pythonw` 的 cp936 标准输出上会把 `javac` 的中文警告打成 `UnicodeEncodeError` 直接中断构建，改成先 `reconfigure(encoding="utf-8")`、再对残余字符兜底转义。
